# 2.0 Football API Proposal

Last reviewed: 2026-07-05

This proposal is a planning document only. It does not implement production code.

## Summary recommendation

Start 2.0A with `football-data.org` as the first provider spike.

Reasons:

- It covers the core target competitions for the first version: Premier League, La Liga, Serie A, Bundesliga, Ligue 1, and FIFA World Cup.
- It has simple competition codes that map well to a small app-owned base competition model.
- Its API shape exposes fixtures, UTC kickoff times, matchday/stage labels, status, and scores in a way that should fit the existing `fixtures` and scoring flow.
- Its free/low-cost model is friendlier for an MVP than a broad live-data provider, as long as the app accepts delayed scores on the free tier or upgrades later for live scores.

Use API-Football as the fallback if the spike proves football-data.org score freshness, World Cup coverage, or selected-fixture batching is not good enough.

## Provider comparison

### football-data.org

Best fit for the first spike.

Relevant strengths:

- Free-tier coverage includes Premier League, Bundesliga, Ligue 1, Serie A, La Liga, and Worldcup.
- Official lookup codes include:
  - Premier League: `PL`
  - La Liga / Primera Division: `PD`
  - Serie A: `SA`
  - Bundesliga: `BL1`
  - Ligue 1: `FL1`
  - FIFA World Cup: `WC`
- Competition matches endpoint supports filters including `dateFrom`, `dateTo`, `stage`, `status`, `matchday`, `group`, and `season`.
- Cross-competition matches endpoint supports `competitions`, `ids`, `dateFrom`, `dateTo`, and `status`, which is promising for selected fixture score sync.
- Match payloads include `utcDate`, `status`, `minute`, `matchday`, `stage`, `group`, `lastUpdated`, teams, and score data.
- Free plan lists fixtures, delayed schedules, delayed scores, league tables, and 10 calls/minute.
- Paid "Free w/ Livescores" is relatively low cost if delayed free scores are not enough.

Risks and unknowns to verify in 2.0A:

- Free-tier score delay may be too slow for a results automation feature.
- Need to confirm if `ids={matchIds}` works for the exact competition set and tier used.
- Need to confirm API response for postponed/suspended/cancelled matches and score corrections.
- Need to confirm 2026 World Cup availability and freshness near tournament time.
- Need to verify whether the provider returns all useful final score fields consistently for league and cup/knockout matches.

### API-Football

Best fallback if live/final score reliability is more important than a minimal provider.

Relevant strengths:

- Official pricing page says all plans include all competitions and endpoints, with free plans limited by available seasons.
- Free plan has 100 requests/day and includes fixtures, livescore, teams, standings, events, lineups, statistics, and predictions.
- Paid plans start with much larger daily request allowances.
- Likely stronger breadth for live-ish scores, fixture status detail, and cross-competition coverage.

Risks and unknowns to verify in 2.0A:

- Free plan daily quota is much tighter than football-data.org for repeated polling.
- Endpoint docs are more dashboard/JS oriented, so the spike should verify exact fixture ID batch support with a real key.
- Wider provider surface may tempt overbuilding. For this app, only fixtures, status, and scores are needed initially.
- Need to map API-Football league IDs and season identifiers for all target competitions.

## Proposed architecture

Keep the app-owned database as the source of truth for user-facing flows.

```text
External football API
  -> protected import/sync route
  -> external fixture cache tables
  -> picker UI reads local cache only
  -> selected fixtures copied/linked into existing fixtures table
  -> protected result sync updates selected local fixtures
  -> existing scoreFixture/recalculateLeaderboard flow
```

Principles:

- Picker UI must never call the provider directly.
- External API keys stay server-side only.
- The app continues to use internal `seasons`, `gameweeks`, `fixtures`, `predictions`, `joker_usage`, and `leaderboard_entries`.
- App gameweeks remain internal. They should not be assumed to equal external matchdays.
- Manual fixtures remain supported for fallback and emergency corrections.
- Result sync should update selected fixtures only, not every cached provider fixture.
- Admin override must remain possible even for API-linked fixtures.

## Proposed DB schema changes

Use a migration in 2.0B after the 2.0A spike confirms provider shape.

### `seasons` additions

```sql
alter table public.seasons
add column if not exists base_provider text,
add column if not exists base_competition_code text,
add column if not exists base_competition_name text,
add column if not exists base_competition_external_id text,
add column if not exists provider_season text,
add column if not exists fixture_import_enabled boolean not null default false,
add column if not exists result_sync_enabled boolean not null default false;
```

Notes:

- `base_provider`: for example `football_data`.
- `base_competition_code`: for example `PL`, `WC`.
- `base_competition_external_id`: provider numeric/string id if needed.
- `provider_season`: provider year or season id. Keep as text because providers differ.
- Booleans let us create fields safely before turning automation on.

### New `external_competitions` table

```sql
create table if not exists public.external_competitions (
  id uuid primary key default gen_random_uuid(),
  provider text not null,
  external_competition_id text,
  external_competition_code text not null,
  name text not null,
  country text,
  type text,
  enabled boolean not null default true,
  display_order integer not null default 100,
  raw_payload jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (provider, external_competition_code)
);
```

Seed candidates for football-data.org:

```text
football_data / PL  / Premier League / England
football_data / PD  / La Liga / Spain
football_data / SA  / Serie A / Italy
football_data / BL1 / Bundesliga / Germany

```

### New `external_fixtures` cache table

```sql
create table if not exists public.external_fixtures (
  id uuid primary key default gen_random_uuid(),
  provider text not null,
  external_fixture_id text not null,
  external_competition_id text,
  external_competition_code text not null,
  provider_season text,
  external_round text,

  external_group text,
```

## Season/base competition model

The season owns the default competition context.

Rules:

- Normal 38-gameweek season: `base_provider = football_data`, `base_competition_code = PL`, `base_competition_name = Premier League`.
- Test World Cup season: `base_competition_code = WC`.
- App gameweeks remain generated internally and assigned to pickers internally.
- External matchday/round is metadata for picker convenience, not the app gameweek number.
- Default picker pool should only include fixtures from the season base competition.
- Manual fixtures can be mixed into a gameweek, but should be visually marked as manual/admin-added later.
- Cross-competition fixture requests should wait for a later version with admin approval.

## Fixture import/cache strategy

2.0B should import upcoming fixtures into `external_fixtures`, not directly into `fixtures`.

Recommended import windows:

- Daily scheduled import for the active season base competition.
- Import `now - 2 days` to `now + 45 days` during a league season.
- On season setup, allow admin to import a wider window, such as the whole provider season, if request limits allow.
- For World Cup, import the full tournament window once available, then refresh daily.

Upsert key:

```text
(provider, external_fixture_id)
```

Import mapping for football-data.org:

- `id` -> `external_fixture_id`
- `competition.code` -> `external_competition_code`
- `season.id` or requested season year -> `provider_season`
- `utcDate` -> `kickoff_at`
- `status` -> cached `status`
- `matchday` -> `external_matchday`
- `stage` -> `external_stage` / `external_round`
- `group` -> `external_group`
- `homeTeam.name` -> `home_team`
- `awayTeam.name` -> `away_team`
- final score fields -> `home_score`, `away_score`
- full row -> `raw_payload`
- sync timestamp -> `last_synced_at`

Status mapping should be explicit and conservative:

```text
TIMED/SCHEDULED -> scheduled
IN_PLAY/PAUSED -> locked or scheduled cache status, not completed
FINISHED -> completed when final score exists
POSTPONED -> postponed
CANCELLED/SUSPENDED/ABANDONED -> void or external-only status pending admin decision
```

Do not overwrite local selected fixture results blindly if an admin has already manually corrected them. Add an override flag later if needed.

## Picker UI strategy

2.0C should improve picker workflow without changing the core rule: selected fixtures live in the existing `fixtures` table.

Flow:

1. Picker opens `/pick-fixtures`.
2. Page loads eligible internal app gameweek as it does today.
3. Page loads cached `external_fixtures` for the active season base competition.
4. Default view groups or filters fixtures by the next useful external round/date cluster.
5. Picker selects four cached fixtures.
6. Save action copies linked data into `fixtures`:
   - teams
   - kickoff
   - competition
   - external provider/id/code/round/matchday/status payload
7. Manual entry remains available as a fallback mode.

Important UI guardrails:

- Do not show unrelated competitions by default.
- Do not hide manual fallback.
- Clearly mark fixtures already selected for this app gameweek.
- Exclude fixtures already linked to another active-season app gameweek unless admin override is added.
- Do not allow picker edits after predictions exist, preserving current safety.
- Do not treat external matchday as app gameweek.

## Result sync strategy

2.0D should sync selected local fixtures only.

Candidate fixtures:

- Active season only.
- `fixtures.external_provider` and `fixtures.external_fixture_id` are present.
- Status is not terminal, or fixture completed recently and may need correction.
- Window starts at `kickoff_at - 30 minutes`.
- Window continues until provider says full time/completed.
- Hard cutoff for normal league fixtures: `kickoff_at + 3h30`.
- Future World Cup knockout hard cutoff can be longer because of extra time/penalties.

Sync behavior:

1. Find candidate selected fixtures.
2. Batch provider requests by fixture IDs when supported.
3. Map provider status/score to local fixture.
4. If provider says completed and scores are present:
   - update `fixtures.status = completed`
   - update `home_score` / `away_score`
   - update external metadata and `external_last_synced_at`
   - call existing `scoreFixture(fixtureId)` logic
5. After processing all changed completed fixtures, call existing `recalculateLeaderboard(seasonId)`.
6. Upsert gameweek-complete activity using the existing activity helper when the internal gameweek is complete.

Duplicate scoring safety:

- Existing scoring recalculates prediction rows for a fixture from current final score, so repeated scoring is safe.
- Leaderboard recalculation rebuilds season totals, so repeated recalculation is safe.
- Still avoid needless writes by only scoring when score/status changed or when the fixture newly becomes completed.

Score correction policy:

- If provider changes a completed score within a correction window, update and rescore.
- After a configurable cutoff, require admin review before overwriting a completed local result.
- Keep manual admin correction as the ultimate source of truth.

## Cron and scheduler recommendation

Use two different scheduling approaches:

### Fixture import

Use Vercel Hobby daily cron because daily import is enough.

Example:

```text
/api/cron/import-external-fixtures
0 7 * * *
```

This can run before the existing 08:00 UTC reminder cron.

### Result sync

Use an external scheduler such as cron-job.org every 15 minutes.

Reason:

- Vercel Hobby cron is daily only.
- Score sync needs short polling during live windows.
- The route itself should remain cheap by refusing to call the provider when no selected fixtures are in the sync window.

Example:

```text
/api/cron/sync-fixture-results
every 15 minutes from cron-job.org
Authorization: Bearer <EXTERNAL_SYNC_SECRET or CRON_SECRET>
```

Do not poll all day blindly. The route should first query local selected fixtures and only call the provider when relevant.

## API call budget estimate

These are rough planning numbers. 2.0A should replace them with measured provider behavior.

### Fixture imports

football-data.org:

- Daily active-season import: 1 call/day if competition/date range endpoint returns all matches in the window.
- Weekly manual admin wider refresh: 1 to 3 calls depending on date windows.
- Monthly whole-season refresh: likely 1 call if the provider allows full season match listing for the competition.
- Budget: 1 to 5 calls/day for imports.

API-Football:

- Similar if fixtures can be fetched by `league + season + date/window`.
- Free quota is 100 requests/day, so daily import is fine, but aggressive polling is not.

### Selected fixture result syncing every 15 minutes

Assume 4 selected fixtures in one app gameweek.

If provider supports batched fixture IDs:

- One poll = 1 API call.
- Matchday active window: about 4 hours from kickoff - 30m to kickoff + 3h30.
- 15-minute interval: about 16 calls per matchday window.
- Split weekend with Saturday/Sunday/Monday fixtures: about 16 calls per active fixture day, so 32 to 48 calls for a spread gameweek.

If provider does not support batched fixture IDs:

- One poll = up to 4 calls.
- 4-hour window = about 64 calls for one fixture day.
- Spread weekend = 128 to 192 calls.

Conclusion:

- Batched selected-fixture sync is strongly preferred.
- football-data.org 10 calls/minute is enough for batched sync and probably enough for 4 individual calls every 15 minutes, but free-tier delayed scores may reduce usefulness.
- API-Football free 100 requests/day is tight if IDs cannot be batched or if fixtures are spread across multiple days. Paid plan would likely be needed for comfortable live-ish sync.

## Timezone handling plan

Keep current core behavior:

- Store `kickoff_at` as a UTC instant.
- Prediction locking remains `kickoff_at <= now`.
- Matchday logic that asks "is this fixture today?" uses `Europe/London`.
- Manual fixture entry continues parsing UK/Ireland fixture times with `fromZonedTime(..., "Europe/London")`.

External provider handling:

- football-data.org `utcDate` should be parsed as an absolute UTC instant.
- API-Football must be tested with explicit timezone behavior. Prefer requesting UTC from the provider if possible.
- Do not parse provider dates as local browser dates.
- Do not use `new Date("YYYY-MM-DD")` for football-day decisions.
- For display, later improve formatting to explicitly use `Europe/London` so users see expected local football times.

## Edge cases to design for

- Split rounds and Monday fixtures.
- Winter breaks.
- Postponed/cancelled/abandoned fixtures.
- Provider changes kickoff time after import.
- Already-picked fixture kickoff changes after users predicted.
- Provider downtime or quota exhaustion.
- Provider score corrections after full time.
- World Cup group and knockout rounds.
- Extra time and penalties.
- App gameweek number not matching provider matchday.
- Manual fixtures mixed with API-linked fixtures.
- Draft/test/archive seasons accidentally syncing or appearing in reminder logic.

Recommended defaults:

- Do not sync draft or archived seasons.
- Do not import for seasons where `fixture_import_enabled = false`.
- Do not result-sync for seasons where `result_sync_enabled = false`.
- Do not overwrite completed local results after a cutoff without admin approval.
- Show provider errors in Admin Maintenance, not to normal users.

## Must-fix risks before implementation

1. Provider score freshness

   Confirm whether football-data.org free delayed scores are acceptable. If not, choose either football-data.org paid livescores or API-Football before building result sync.

2. Batch selected-fixture sync

   Confirm whether the chosen provider can fetch 4 to 5 selected fixture IDs in one call. This materially affects request budget.

3. Provider status mapping

   Build and test a small explicit mapping before touching local `fixtures.status`.

4. Admin/service-role protection

   Import and sync routes must use server-side secrets only and fail closed when provider keys or cron secrets are missing.

5. Scoring function reuse

   Current scoring helpers live inside `app/(app)/admin/actions.ts`. Before 2.0D, extract shared server-only scoring helpers to avoid route/action duplication.

6. Manual override semantics

   Decide how to prevent automated sync from overwriting an admin-corrected result. A minimal first version can avoid overwriting completed fixtures after a correction cutoff.

7. Environment documentation

   Add provider env vars to Operations before enabling routes:

   ```env
   FOOTBALL_DATA_API_KEY=...
   FOOTBALL_API_PROVIDER=football_data
   EXTERNAL_SYNC_SECRET=...
   ```
